# 运营模式

## 对象与数据

- 从业务用户的决策和工作流选择对象类型；对象可以表示实体或事件。对象类型不是数据集的机械复制。
- 记录主键、业务身份、属性类型与数据源映射；验证空值、重复键、删除、刷新和合并。主键识别单个类型内对象，不自动解决跨源实体同一性。
- 主键须唯一且确定性生成；不要每次刷新重新用行号或随机数生成，否则可能丢失编辑和链接。修改现有类型主键可能涉及既有编辑删除，先核对影响并取得明确授权。
- 链接定义两端类型、方向、基数及实现方式；按实际 Foundry 配置确认来源和维护方式，不宣称所有链接都有同一种存储实现。
- 当前官方文档中的 one-to-one 基数只标示意图，并不强制执行；有唯一关系要求时须补充数据与操作校验。
- 有独立属性、时间或生命周期的关联可建成对象，例如“工单指派记录”；当前负责人和历次指派不能混为一条无时间关系。
- 只有共享能力确有消费方时才引入接口或共享属性；接口多态不能照搬 OWL 的逻辑子类推理。

## 行动契约

行动应命名为业务意图，如“指派工单”，而不是抽象“更新字段”。对每个行动记录：

| 项目 | 必须明确的内容 |
| --- | --- |
| 输入与目标 | 参数、作用对象、可变属性和链接 |
| 准入 | 参数合法性、当前状态、业务前置条件、submission criteria |
| 授权 | 谁能看对象、谁能执行行动、所需资源权限；界面隐藏不能替代授权 |
| 修改 | 状态前后、规则或函数、受影响对象和链接 |
| 副作用 | 通知、webhook、外部权威系统及执行顺序 |
| 失败与重复 | 并发、重试、重复提交、外部超时的处理责任及需验证的保证 |
| 反馈 | 行动记录、读取更新、审计、外部确认与业务结果 |

submission criteria 是提交条件，不是整个权限体系。函数可以计算或参与行动逻辑，但仅定义函数不等于建立行动契约。

Foundry 的行列读访问控制不自动延伸到行动写入及下游数据；按官方权限模型检查 markings、分类访问控制和读写授权。通知接收者也须有内容访问权限；通知发送失败时，对象编辑仍可能成功。测试应分别检查读取、执行、写入传播与副作用，而不是只测试按钮可见性。

## 写入边界

- 核实数据集输入、用户编辑与读取结果的协调方式，不假设刷新自动覆盖或保留所有编辑。
- 明确 Foundry 与外部系统中谁是事实权威、谁接收写入。对象编辑不自动意味着源系统已更新。
- 官方将 Action 描述为单次事务；不要将其推广为外部 webhook、通知和源系统更新的全局 ACID 或恰好一次保证。
- 原子性、可见性延迟、冲突策略、失败回滚、重试和审计能力按实际版本与配置验证；无法确认时保留为未决问题，不虚构平台开关。

## 最小纵向验证

自行构造示例：“指派工单”改变负责人及相关链接，未关闭工单且授权人员才可提交；是否需要外部写入由业务决定。

- 正常：授权用户指派给有效员工，属性/链接按契约更新并可读取。
- 异常：无权用户、无效员工、关闭工单、非法参数均按契约被拒绝。
- 边界：同时指派、重复提交、数据刷新、对象删除、外部超时；记录实际行为、业务可接受结果和补偿责任。
- 联合模式：将一次行动表示为 RDF 事件只用于描述和查询，不自动执行行动；类型和权限两侧分别验证。

未连接 Foundry 时输出设计与测试计划，不声称已经部署或平台测试通过。官方依据见[研究来源](../../../research.md)。
