# 技能元编排

用于跨产品、系统、应用、语义、项目和实现边界的复杂任务。它管理“调用哪些能力、以什么顺序、交接什么结果、何时停止或回退”，不直接替代下游 Skill 的专业判断。

## 调度协议

1. 先判断任务规模：单一能力可完成时只调用一个 Skill；只有存在跨域依赖、阶段交接或互相约束时才建立多 Skill 调度。
2. 把用户目标拆成决策问题和可验证产物，区分事实、假设、未知、证据和决策；不要按技术名词机械路由。
3. 选择一个主 Skill 或主 Agent 负责收敛。专项 Skill 只回答会改变当前决策的问题，不生成互相竞争的完整方案。
4. 建立最小任务图：每个节点记录输入、输出、前置条件、责任方和验证方式；有依赖的节点顺序执行，只有互不依赖的证据收集才并行。
5. 每次交接都传递事实、假设、证据、决策、风险、未决问题、验证状态和下一步入口。下游不得把上游假设升级为事实。
6. 在每个阶段设置质量门：若证据不足但会改变方向，暂停并集中提问；若验证推翻上游判断，回退到最小受影响节点，不重跑无关工作。
7. 任务完成条件是主目标已验证、交接产物可追溯、剩余未知项有责任人和验证条件；达到条件后停止调度，不为了填满流程继续调用 Skill。

## 常用路由

- 产品问题：`product-thinking` 及其发现、结果、假设和优先级专项。
- 系统边界、概念和复杂度：`system-architecture-product-design` 能力域。
- 领域、数据、运行和平台：`enterprise-application-architecture` 能力域。
- 语义、身份、关系、规则、RDF/OWL/SHACL 或对象/链接/行动：`ontology-modeling`。
- 软件结构、契约、验证和项目网络：`architecture-way` 能力域。
- 跨生命周期路由：`software-engineering-process`；代码、文档或配置变更的执行约束：`engineering-task-discipline`。

上述只是路由提示。领域边界不清时先补系统或产品上下文，不默认微服务、云、知识图谱、OWL 推理器或某种平台。

## 输出契约

用中文输出：

- 当前目标、范围、成功标准和关键未知；
- 主 Skill/Agent、专项 Skill、调用顺序及可并行节点；
- 每个节点的输入、输出、责任方和验证方式；
- 当前状态中的事实、假设、证据、决策、风险和交接字段；
- 质量门、停止条件、回退触发器和下一步行动。

若任务只有一个明确 Skill 能完成，直接说明“单 Skill 路由”和验证方式，不创建无意义的调度图。
