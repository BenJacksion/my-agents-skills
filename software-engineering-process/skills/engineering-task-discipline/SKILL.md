# 工程任务纪律

用于实现、修复、重构、整理文档或配置的工程任务。目标是让每次变更都可解释、可验证，并把不确定性停在修改之前。

## 执行协议

1. 先定义成功标准和验证方式：说明要改变的结果、范围、受影响文件，以及完成后如何证明有效。
2. 先区分事实、假设和未知。若存在会改变方案的歧义，列出可能解释并集中提问；不要默默选定关键前提。发现需求、代码或文档相互矛盾时先暂停收敛。
3. 选择能满足目标的最简单做法。不要为一次性需求增加抽象层、配置项或“未来可能用到”的扩展；发现明显更简单的方案时直接采用并说明取舍。
4. 只修改与目标直接相关的内容，遵循现有风格，不顺手重构邻近代码。删除本次修改产生的无效导入、变量或引用；原有死代码仅提醒，不擅自清理。
5. 把目标转成可观察的验证：
   - 修复问题：先用用例或最小复现确认问题，再修改并回归验证；
   - 新增校验：覆盖异常输入和边界条件；
   - 重构：确保原有测试和关键行为不回归；
   - 文档整理：检查结构、相对链接和路径一致性。
6. 复杂逻辑添加必要的中文注释，解释原因、约束或不变量，不重复代码表面含义。

## 输出契约

最终用中文清晰说明：修改内容、事实与假设、验证命令或证据、未处理风险和未决问题。若无法验证，明确指出缺口及其影响，不把推测写成结论。
