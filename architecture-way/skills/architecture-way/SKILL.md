# 架构之道

把软件开发看成两个相互约束的设计问题：

- **系统设计**：系统如何分解、组合、变化和交付功能；
- **项目设计**：团队如何组织活动、依赖、人员、时间、成本和风险以完成系统。

不要只画架构图，也不要只排项目计划。先找出会改变系统或项目结果的关键决策，再让系统结构、验证活动和项目网络相互校验。

## 工作模式

根据任务选择一种模式：

1. **系统设计**：目标、需求和变化来源已知，但结构或服务边界不稳定。
2. **项目设计**：系统边界基本确定，需要估算、排网、压缩时间或比较执行方案。
3. **综合设计**：系统结构和项目方案会相互影响，需要同时处理分解、组合、验证和计划。
4. **跟踪与纠偏**：已有项目数据，需要更新剩余工作、关键路径、成本、风险和预测。

## 执行协议

1. 开头列出事实、假设、未知、约束和决策期限。
2. 描述系统目标、关键受益者、主要功能、变化来源和现有结构；不要把实现名词直接当需求。
3. 对结构问题调用 `volatility-decomposition`，明确按什么变化或易变性建立边界。
4. 对组合和变化传播问题调用 `composable-architecture`，检查服务契约、共享状态和跨边界行为。
5. 对关键行为调用 `architecture-validation`，验证架构是否能承载目标、契约和必要质量属性。
6. 对项目问题调用 `project-design`，建立活动网络、估算工作量、识别关键路径，比较时间、成本和风险不同的选项。
7. 交付推荐方案时保留被考虑过的替代方案、计算假设、模型局限、复审条件和下一步行动。

## 判断原则

- 不默认采用功能分解、领域分解、微服务或某种平台；边界必须由变化、组合和验证证据支持。
- 不把项目“快速开始”误认为系统设计完成；无法独立交付的功能片段不自动等于价值。
- 不用单一工期、人数或成本数字掩盖网络依赖、风险和资源限制。
- 不把风险当成时间和成本的附属项；不同方案应在时间、成本和风险空间中比较。
- 计算结果用于缩小选择空间和暴露敏感决策，最终取舍仍需由有权限的决策者确认。

## 最小交付

- 系统设计与项目设计的范围和假设；
- 变化/易变性与边界判断；
- 关键服务、契约和组合场景；
- 架构验证和未验证风险；
- 项目网络、关键路径、时间/成本/风险选项；
- 推荐与不推荐选项的理由；
- 跟踪指标、复审条件和未决问题。

## 质量门

交付前确认：

- 结构选择能追溯到变化、目标或约束；
- 契约能解释跨边界组合，而不仅是数据字段；
- 关键架构行为有验证行动或证据；
- 项目方案至少说明网络、资源、时间、成本和风险；
- 不确定的估算和判断没有被写成事实。
