# 项目设计

项目设计把“要构建什么”转成“由谁、以什么依赖、用多少时间和成本、承担什么风险来完成”。它不是把架构交付后机械地排日历，而是从系统结构、服务、契约和验证活动推导执行网络。

## 执行步骤

1. 定义成功：交付范围、质量、可运行性、业务/用户目标、时间窗口、成本边界和风险容忍度。
2. 从架构和验证结果识别活动、交付物、前置条件、人员角色、服务/开发工作、外部依赖和验收条件。
3. 为活动估算工作量和资源，记录估算方法、范围、置信度、不可用资源和关键假设；不要把工作量直接当日历工期。
4. 建立项目网络，计算关键路径和各活动浮动时间，识别资源冲突、串行化瓶颈和可能的高风险活动。
5. 形成至少一个正常执行方案和必要的替代方案，例如不同人员配置、网络压缩、分层执行或风险分解；写出每个方案的前提。
6. 比较方案的时间、成本、风险、质量、资源可用性和成功条件，必要时使用时间-成本、时间-风险或风险交叉点分析。
7. 选择当前方案并保留被放弃选项、机会成本、决策责任人、触发条件和复审日期。
8. 执行期间跟踪活动状态、实际工作量、剩余工作、进度、成本、关键路径和风险，更新预测并触发纠偏。

## 核心模型

### 网络与关键路径

网络表达活动依赖，不是任务清单。至少区分：

- 活动、交付物和完成标准；
- 前置/后置关系；
- 资源约束；
- 关键路径；
- 总浮动时间和自由浮动时间；
- 外部依赖和风险缓冲。

不能用“增加开发者”自动缩短关键路径；先检查活动是否可并行、沟通是否增加、资源是否稀缺以及依赖是否真正解除。

### 时间、成本与风险

项目选项可视为时间、成本和风险的组合。压缩计划可能增加人员协调、返工、技术风险和失败概率；延长时间或减少并行也可能降低风险。比较时明确：

- 交付时间与关键里程碑；
- 人员、服务、工具和外部采购成本；
- 风险来源、概率/影响或成功概率的模型；
- 质量、范围和运营准备的影响；
- 何时重新计算或切换方案。

风险计算必须保留模型、数据来源和不确定性。没有数据时，输出定性等级或范围，不伪造精确概率。

### 跟踪与预测

跟踪不只报告“完成百分比”。结合活动状态、实际投入、剩余工作、进度和成本形成预测；当实际趋势使关键路径、预算、风险或质量承诺失效时，重新评估执行选项。

## 输出

- `success_definition`：成功、范围、质量和护栏；
- `activity_register`：活动、交付物、估算、资源和完成标准；
- `project_network`：依赖、关键路径、浮动时间和外部约束；
- `project_options`：正常、压缩、风险分解或其他可行方案；
- `time_cost_risk_analysis`：方案比较、模型、假设和敏感性；
- `tracking_plan`：状态、预测、纠偏和复审触发条件；
- `handoff`：责任、决策和执行前置条件。

## 约束

- 不把估算当承诺，不把单一计划当事实；
- 不为了时间压缩而隐去质量、验证、风险和返工；
- 不用平均人月掩盖关键路径、人员技能和依赖关系；
- 不以算法或电子表格输出替代项目负责人对风险的判断；
- 项目设计必须能回溯到系统设计和验证活动；若活动来源不明，回退架构或范围澄清。

## 质量门

- 活动网络可解释，关键路径和浮动时间可复核；
- 每个重要估算有方法、范围、置信度和假设；
- 至少比较时间、成本和风险不同的可行选项；
- 风险会影响方案选择或复审，而不是停留在清单中；
- 跟踪数据能更新剩余工作和预测，并有明确纠偏动作。
