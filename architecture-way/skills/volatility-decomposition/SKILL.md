# 易变性分解

分解的目的不是让组件数量更多，而是让变化尽量局部化，让系统更容易组合、验证、维护和演化。先识别什么会变、变化从哪里来、变化会影响哪些功能和关系，再决定边界。

## 执行步骤

1. 收集需求变化、业务规则、用户行为、技术平台、外部系统、法规、数据格式、部署环境和运营策略等变化信号。
2. 为每个变化信号记录影响对象、发生频率或不确定性、影响范围、提前可知程度、变化代价和证据。
3. 检查当前是否按功能名、部门、数据表或页面直接切分；这类切分只能作为现状描述，不能自动作为推荐结构。
4. 比较候选边界：变化是否局部化、跨边界组合是否增加、接口和测试成本是否可接受、系统级行为是否仍能表达。
5. 形成层、组件或服务候选，并说明每个候选承载的功能、变化、依赖、状态和验证边界。
6. 检查开放与封闭关系：对稳定契约开放组合，对高易变实现封装；不要为了“可扩展”预先引入没有证据的抽象。
7. 用至少一个典型变化场景和一个异常/回滚场景验证边界；保留未决的边界争议。

## 输出

- `volatility_register`：变化来源、易变性判断、证据和置信度；
- `decomposition_options`：至少一个现状结构和一个候选结构；
- `structure`：层、组件/服务、职责、状态和依赖；
- `boundary_rationale`：边界如何局部化变化及其代价；
- `composition_risks`：跨边界组合、重复逻辑、共享状态和故障传播风险；
- `validation_actions`：需要用场景、原型或运行证据验证的判断。

## 约束

- “按易变性”是边界判断依据，不是按关键词给组件命名的规则。
- 不把业务领域、团队边界或数据库表直接等同于架构边界。
- 不把每个变化点都单独拆成服务；接口、部署、观测、测试和运营成本必须计入。
- 不把局部可变性误认为系统级变化已被隔离；检查变化通过契约、工作流和数据传播的路径。
- 只有在目标、变化证据和验证边界都明确时，才给出推荐分解。

## 质量门

- 每个关键边界至少连接一个明确变化信号；
- 说明拆分带来的新增接口、协调、部署和测试成本；
- 至少检查一个跨边界完整场景；
- 能解释为什么现状功能分解会导致重复或变化传播，或者明确说明它并不存在该问题；
- 推荐不是唯一真理，保留替代结构和复审触发条件。
