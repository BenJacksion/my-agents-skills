## 第一部分：架构设计方法论

### 第 1 章：架构师的修炼

#### 软件架构

软件架构不是架构图、技术中台、微服务或 Kubernetes 的名称，而是对以下内容的总体决策：

- 系统功能；
- 数据组织；
- 代码组织；
- 运行方式；
- 部署方式。

常见误区：

- 把使用 Spring Cloud 或 Kubernetes 当成架构；
- 把架构图当成架构本身；
- 把上一项目的经验直接套到当前项目。

#### 架构师职责与思维

合格架构师同时承担三类职责：

1. 在需求与研发之间翻译业务和技术；
2. 处理关键技术问题；
3. 规划系统长期演进。

核心思维：

- 抽象：识别不变部分并隔离变化；
- 分治：把大系统拆成可理解、可验证的部分；
- 成本：在约束下寻找合适方案，而不是追求抽象的“最好技术”；
- 演进：今天的方案要为明天保留合理的变化空间。

顶级架构师应能在业务和技术之间双向翻译，不盲目追新技术，有前瞻性但采用分阶段落地，并抓住问题本质而不是堆叠术语。

#### 五视图法

| 视图 | 主要回答 | 典型产物 |
| --- | --- | --- |
| 逻辑架构 | 系统做什么 | 用例、领域模型、子域、限界上下文 |
| 数据架构 | 数据如何组织 | 表、聚合、NoSQL、数据流转 |
| 开发架构 | 代码如何组织 | 分层、模块、中台、框架 |
| 运行架构 | 系统如何稳定运行 | 并发、一致性、容错、限流 |
| 物理架构 | 系统部署在哪里 | 机器、网络、容器、容灾 |

五视图不是机械的串行瀑布：逻辑架构通常先启动，其余视图应根据约束并行深化并相互校验。

### 第 2 章：逻辑架构设计

#### 用例模型

用例的基本要素是 Actor、Use Case 和 System Boundary。分析可以由粗到细：

1. 业务用例：从业务角色和业务目标描述；
2. 系统用例：从系统责任描述；
3. 用例描述：补充前置条件、后置条件、主流程和异常流。

事件流至少包括主成功场景和扩展场景。逻辑架构的产物包括业务需求列表、需求规格说明和后续领域模型的输入。

用例不是功能清单，而是角色通过系统达成目标的行为描述。

#### 界面原型

原型的价值不是视觉美观，而是：

- 提前验证业务闭环；
- 帮助领域对象和业务状态显现；
- 暴露职责边界和交互缺口。

#### 领域模型与变更

软件退化通常来自需求持续增加、层间穿透、业务规则散落在 Controller、Service 和 SQL 中，以及局部修改造成大范围回归。

功能开发和结构重构是两顶不同的帽子，不应在同一变更中混淆：

1. 先让新功能正确落地；
2. 再识别坏味道并小步重构；
3. 用测试、编译和可运行结果保护重构。

关键概念：

- 统一语言；
- 实体：具有身份和生命周期；
- 值对象：没有独立身份，属性相同时相等；
- 领域服务：承载跨实体、无状态的领域行为；
- 聚合与聚合根：维护一致性边界和不变量；
- 仓库与工厂：隔离持久化和复杂对象创建；
- 限界上下文：维护一套统一语言和模型边界，是服务边界的重要来源。

技术可行性在逻辑阶段就要检查实时性、合规性、性能上限和第三方能力边界，否则数据、运行和部署视图可能整体返工。

### 第 3 章：数据架构设计

推荐追溯链：

```text
领域模型 -> 聚合边界 -> 存储模型 -> 读写模型 -> 数据流转
```

先领域、后表；先业务边界、后分库分表。

数据库设计需要处理一对一、一对多、多对一、多对多和继承关系。继承关系可根据查询、扩展和一致性需求选择单表加类型字段、子类表或类表继承。

NoSQL 选择应从访问模式和数据关系出发：

- 文档库：聚合或文档整体读写；
- KV：高频读、弱结构；
- 图数据库：关系网络；
- 列族数据库：海量写入或分析场景。

领域程序设计需要区分实体、值对象和领域服务。贫血模型不是绝对错误：

- 核心域应尽量让行为靠近领域对象；
- 通用域和支撑域可以采用更简单的贫血结构；
- 不应把充血或贫血作为脱离上下文的教条。

聚合是强一致边界，聚合根负责守护不变量。跨聚合不应默认使用强一致事务，而应根据场景选择事件、补偿和最终一致性。

领域层不应依赖 MyBatis、JPA 或 Mongo 等持久化细节。不同限界上下文中的同名概念可能含义不同，上下文之间可通过防腐层隔离模型污染。

### 第 4 章：开发架构设计

系统规划应比较自研、接入平台、采购和外包。接口设计中，语义先于格式；DTO 不等于领域对象；对外契约应稳定，内部实现可以替换。

传统的 `Controller -> Service -> DAO` 容易造成业务层依赖基础设施。整洁架构可按以下方向组织：

```text
领域层（最内）
应用层（用例）
接口层（适配器/控制器）
基础设施层（数据库/消息/缓存）
```

依赖从外层指向内层，内层不认识外层。这样可以降低数据库和 Web 框架替换对业务逻辑的影响，并改善测试和遗留演进。

技术中台不是简单再包一层 Spring。它应复用真正稳定且可运营的能力，例如事务、审计、版本、查询、导出、权限、领域事件、仓储、注册、配置、网关和链路能力。判断标准是业务线是否只需编写差异、新业务能否更快交付、公共问题能否集中修复。

技术选型顺序：

1. 明确问题；
2. 明确约束；
3. 比较市场方案；
4. 检查团队是否能维护；
5. 评估退出成本。

通用能力优先复用或采购，差异化业务能力才考虑自研。模块划分优先按业务域和职责，而不是按技术层；跨模块通过接口协作，不直接穿透实现类。

### 第 5 章：运行架构设计

运行架构应采用“属性 -> 场景 -> 决策”：

```text
非功能属性
  -> 具体场景（大促下单、对账批处理、报表导出）
  -> 架构决策（缓存、异步、分库、读写分离、限流）
```

非功能需求至少覆盖：

- 性能：TPS、QPS、响应时间；
- 可用性：SLA、容灾、降级；
- 安全：鉴权、审计、合规；
- 可维护性：日志、监控、灰度；
- 可扩展性：加机器、加租户、加业务。

架构粒度应随业务复杂度、团队规模、组织边界和交付节奏调整。小系统采用微服务会引入不必要的网络、部署和运维复杂度，大系统长期维持没有边界的单体也会阻塞演进。

运行架构还要处理意图架构、架构跑道、使能故事、技术架构演化以及遗留系统改造。遗留改造可按以下方式渐进进行：

1. 补足边界；
2. 抽取稳定共性；
3. 增加防腐层；
4. 新老结构并存；
5. 逐步切换流量；
6. 退役旧模块。

### 第 6 章：物理架构设计

集中式架构通常更简单，事务和运维成本更低，但扩展受单机或集中节点限制。分布式架构有利于扩展和组织并行，但会引入网络不可靠、一致性、观测和运维问题。

物理架构不应先从服务器数量开始，而应说明：

- DMZ、内网和数据区；
- 防火墙与负载均衡；
- 多可用区；
- 容量规划；
- 容灾和切换。

应由业务规模、可用性、组织和交付约束推动分布式，而不是因为技术流行而分布式。

## 第二部分：分布式架构设计与实践

### 第 7 章：分布式架构设计

#### 分布式架构演进

常见演进路径：

```text
单体
-> 读写分离
-> 加缓存
-> 垂直拆分
-> SOA/RPC
-> 微服务
-> 容器化/云原生
```

每一步都要回答：

- 当前性能瓶颈是什么？
- 是否存在团队或组织瓶颈？
- 发布是否成为瓶颈？
- 数据规模和数据访问是否成为瓶颈？
- 新机制引入了什么一致性、运维和排障成本？

#### 高并发与高可用

架构手段必须由场景驱动：

- 缓存：读多写少或热点数据；
- 异步：解耦和削峰；
- 分库分表：数据量或写入规模超过单库能力；
- 读写分离：读多写少；
- 限流：保护系统；
- 熔断：阻止故障扩散；
- 降级：保护核心链路；
- 幂等：应对网络重试和重复投递；
- 最终一致：跨服务场景不盲目追求分布式强事务。

每个机制都要说明触发场景、保护对象、失效模式、恢复方式和度量指标。

### 第 8 章：微服务架构设计

微服务的前提包括：

- 领域边界清楚；
- 注册、配置、网关和链路治理能力可用；
- 团队具备服务运维能力；
- 组织和服务责任基本匹配。

微服务设计还要处理领域边界、统一语言、服务责任、注册中心、配置、网关、链路治理、测试和调优。微服务不是单独的部署技术，拆分应同时解释业务变化、交付效率、组织责任和运行治理。

### 第 9 章：基于云端的分布式部署

云原生不等于“上 Kubernetes”，还包括容器、编排、服务治理、可观测性、弹性和声明式部署。对有状态组件、网络、权限、数据迁移、备份恢复和成本必须单独建模。

## 第三部分：大数据架构设计

### 第 10 章：大数据时代变革

大数据时代的变化不只是增加 Hadoop 组件，而是推动企业从数据支撑 IT 转向数据驱动业务，逐步形成数据采集、清洗、存储、计算、服务和治理的完整能力链：

```text
采集 -> 清洗 -> 存储（湖/仓/实时）-> 计算 -> 服务 -> 治理
```

主线是：

```text
业务域 -> 指标域 -> 数据模型 -> 数据 API
```

### 第 11 章：大数据技术中台

大数据平台和数据中台不是同一个概念。大数据技术中台需要在基础算力和存储之上，继续建设面向业务和分析使用的数据能力：

| 大数据平台 | 数据中台 |
| --- | --- |
| 提供算力和存储 | 提供可复用的数据能力 |
| 主要面向工程师 | 服务业务、分析和前台应用 |
| 偏组件和基础设施 | 偏指标、标签、画像和统一口径 |

建设顺序可按以下阶段推进：

1. 数据标准；
2. 数据质量；
3. 主数据；
4. 指标体系；
5. 标签和维度；
6. 数据服务化；
7. 分析、智能和决策应用。

## 全书工作流

```text
需求/用例/原型
-> 逻辑架构（领域模型/子域/限界上下文）
-> 数据架构（聚合/表/NoSQL/一致性）
-> 开发架构（分层/整洁架构/中台）
-> 运行架构（场景化非功能）
-> 物理架构（部署/网络/容灾）
-> 演进（架构跑道/使能故事/演化式重构）
```

## 可直接复用的判断原则

1. 架构是总体决策，不是画图。
2. 五视图缺少一个，系统就可能在另一个维度积累债务。
3. 逻辑架构先起，其余视图并行深化。
4. 用例是角色达成目标，不是功能数量。
5. 软件退化来自持续加功能而不治理结构。
6. DDD 是建模方法，不是微服务的同义词。
7. 先领域后数据库，先边界后分库分表。
8. 贫血不是原罪，核心域才需要重点承载行为。
9. 聚合是强一致边界，跨聚合通常通过事件和最终一致协作。
10. 限界上下文是微服务边界的重要来源。
11. 整洁架构让依赖指向业务而不是框架。
12. 技术中台的目标是让业务线只编写差异。
13. 技术选型先看约束，再看热度。
14. 没有场景的运行架构只是展示材料。
15. 小系统不要无证据地微服务化，大系统不要长期维持无边界单体。
16. 架构跑道优于一次性大重写。
17. 遗留改造应补边界、加防腐层并逐步切换。
18. 分布式既解决技术问题，也可能解决组织和交付问题。
19. 数据中台是能力复用，不是重新堆一套大数据组件。
20. 恰如其分是架构判断的重要质量标准。
