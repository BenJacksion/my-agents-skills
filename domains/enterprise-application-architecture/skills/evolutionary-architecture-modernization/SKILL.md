# 架构演进与遗留现代化

把演进问题拆成四种结构：

```text
当前架构 -> 目标架构 -> 过渡架构 -> 可验证改造行动
```

## 执行协议

1. 记录当前逻辑、数据、开发、运行和物理架构，以及已知断裂和遗留约束。
2. 把“性能差”“不易扩展”“难以发布”等形容词改写成“属性 -> 场景 -> 决策”：触发、环境、响应、度量、失败阈值和对应架构选择。
3. 说明目标架构要改变的责任、数据、依赖、运行机制和部署边界。
4. 设计一个或多个过渡结构，识别双写、兼容层、旁路、迁移、回滚和并行运行风险。
5. 将改造拆成可独立验证的使能故事/行动；每个行动必须有完成条件和停止/回退条件，并说明它为哪个业务交付或后续演进铺路。
6. 比较渐进重构、局部替换、绞杀式迁移和重写等方案，不把“重写”当作默认正确。
7. 建立复审触发器：指标、故障、数据迁移、团队能力或业务变化发生时重新评估。

## 判断原则

- 目标架构没有过渡结构，就不能称为可执行的演进方案。
- 非功能目标要能指导运行和物理决策，并能被验证。
- 意图架构说明要去哪里，架构跑道说明如何在持续交付中为后续变化保留空间。
- 兼容层和临时结构也要有所有者、移除条件和过期时间。
- 不能因为目标架构更干净就忽略迁移期间的数据、一致性和发布风险。

## 最小交付

- 当前/目标/过渡架构；
- 质量属性场景与基线；
- 改造步骤、依赖、风险和回滚点；
- 每个阶段的验证标准和停止条件；
- 复审触发条件与责任人。
