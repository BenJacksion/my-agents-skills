# 数据平台架构

先确定数据消费者和数据价值，再设计链路、治理和技术承载：

```text
来源 -> 采集 -> 治理 -> 存储/加工 -> 标签/索引 -> 数据服务/分析 -> 反馈
```

## 执行协议

1. 列出数据消费者、业务问题、时效性、粒度、数据规模、保留期、敏感性和合规要求。
2. 识别来源、采集方式、质量规则、主数据/事实数据、所有者和生命周期。
3. 设计清洗、标准化、血缘、元数据、质量监控、权限和审计。
4. 比较数据仓库、数据湖、数据中台或局部数据产品等候选，不先锁定 Hadoop、Spark、HBase 或其他工具。
5. 为标签、索引、多维分析、报表、检索或在线服务明确读写路径和延迟目标。
6. 处理重复、迟到、修订、删除、回溯、重算、数据漂移和上下游契约。
7. 区分“大数据平台”和“数据中台”：前者偏算力与存储，后者偏可复用数据能力、指标、标签、画像和统一口径。
8. 建立“业务域 -> 指标域 -> 数据模型 -> 数据 API”的追溯链，明确指标口径、数据产品消费者和 API 责任。
9. 输出数据责任矩阵、分层/链路、平台范围、服务接口、质量指标和验证行动。

## 判断原则

- 数据平台不是数据仓库、工具集或组织名称的同义词；必须有可交付的数据产品或数据服务。
- 数据中台不是重新堆一套 Hadoop；应先建立标准、质量、主数据、指标、标签和数据服务。
- 数据治理必须落到责任、规则、血缘、质量指标和处理动作。
- 离线分析、实时服务和在线事务对一致性、延迟、存储和模型有不同要求。
- 标签、索引和宽表是服务特定查询或分析场景的手段，不应无目的扩张。
- 数据规模不能单独证明需要大数据技术；成本、运维和团队能力同样重要。

## 最小交付

- 消费者、业务问题和数据产品；
- 来源、采集、治理、存储、加工和服务链路；
- 业务域、指标域、数据模型、数据 API 和血缘追溯；
- 数据所有权、质量、血缘、权限和生命周期；
- 技术候选与范围取舍；
- 延迟/准确性/完整性验证、风险和复审条件。
