# 可组合架构

组件是否“完成”不能只看它能否单独运行，还要看它能否在真实系统场景中与其他组件组合。可组合设计关注行为、契约、状态、异常、顺序和变化传播，而不只是接口数量。

## 执行步骤

1. 列出需要组合的系统级场景，并标出参与的组件/服务、操作者、外部系统、数据和关键状态变化。
2. 区分功能交互与纯数据读写：优先表达触发行为、责任、前置条件、结果、异常和补偿。
3. 审查每个契约的语义、生命周期、版本、幂等性、时序、失败责任、可观测性和安全约束。
4. 追踪一项需求或变化穿过哪些服务、客户端、数据库、消息和运营流程，识别重复实现与隐藏编排。
5. 检查客户端是否承载本应由系统服务协调的业务规则；检查多个服务是否各自重复通知、校验、数据转换或错误处理。
6. 评估契约是否足够稳定、组合是否足够清晰、变化是否局部化；必要时比较集中协调、服务组合和异步协作等不同选项。
7. 用代表性端到端场景验证：正常路径、部分失败、重试、并发、版本变化和撤销/补偿。

## 契约设计

至少说明：

- 提供者与消费者；
- 触发动作和业务语义；
- 输入、输出和状态变化；
- 前置条件、后置条件和不变量；
- 同步/异步、时序和超时；
- 错误、重试、幂等和补偿；
- 版本兼容与迁移；
- 权限、审计、监控和责任边界。

数据字段清单不能替代上述契约。若只共享数据库或只传递 CRUD 状态，必须说明为什么不会丢失业务行为和系统完整性。

## 输出

- `composition_scenarios`：跨组件的代表性场景；
- `contracts`：契约语义、责任、状态、异常和演化规则；
- `change_propagation`：变化影响路径和局部化程度；
- `composition_options`：不同组合方式的取舍；
- `contract_risks`：隐藏编排、共享状态、重复逻辑和版本风险；
- `validation_actions`：需要执行的端到端验证。

## 约束

- 不因“服务化”或“复用”本身判定设计更好；
- 不把一个巨型服务拆成很多薄服务后宣称已经可组合；
- 不把接口可调用等同于业务可组合；
- 不为了避免重复而引入跨领域共享状态或难以演化的通用契约；
- 组合边界应与 `volatility-decomposition` 的变化判断和 `architecture-validation` 的证据互相校验。

## 质量门

- 每个关键契约至少有一个真实组合场景；
- 失败、重试、版本和责任没有被省略；
- 关键业务规则没有在多个消费者中复制；
- 变化传播路径可解释，且有局部化或接受其传播成本的理由；
- 契约复杂度、运行成本和验证成本与复用收益相称。
