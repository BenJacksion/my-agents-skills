# 复杂系统架构

将架构视为一组早期、高影响、变更代价高的决策。架构工作的目标是解决歧义、聚焦创新、简化复杂度，使系统通过形式承载功能并向受益者交付价值。

## 选择工作模式

- **分析已有系统**：从形式入手，识别形式对象、关系、伴生系统、边界和使用情境；再分析功能及形式-功能映射。
- **创建新系统**：从受益者、利益相关者和需求入手，把需求转换为目标；生成多个概念，再形成架构。
- **支持架构决策**：当候选组合较多时，建立决策、选项、约束和衡量指标，探索权衡空间。

若问题只是明确架构下的局部编码或配置，直接处理局部任务，不套用完整流程。

## 共同原则

1. **涌现**：从实体功能及实体间的功能交互推断系统级功能、行为、性能和失效。
2. **整体**：同时观察上层系统、当前系统和下层实体，不把局部最优当作整体最优。
3. **聚焦**：只深入决定价值、性能、成本、风险或演化的少数关键问题。
4. **二元**：人造系统同时存在于物理领域和信息领域；软件也有形式、关系和边界。
5. **受益与价值**：识别价值相关操作数及其跨越系统边界的变化；价值是有成本的利益。
6. **解耦功能与方案**：先形成与特定解决方案无关的功能，再探索概念与形式。
7. **演化**：理解遗留元素，把稳定部分定义为接口，使元素能够演化。
8. **复杂度约束**：区分必备复杂度、实际复杂度和表面复杂度，使实际复杂度尽量接近必备复杂度。

## 按问题加载方法

| 当前缺口 | 专项 Skill | 当前步骤的完成条件 |
| --- | --- | --- |
| 系统层级、边界、涌现不清 | `system-thinking-emergence` | 上下文和关键交互可解释，未知项有验证方式 |
| 已有形式、功能、接口缺少追溯 | `architecture-analysis-mapping` | 主要价值能追溯到功能、形式和边界 |
| 目标、策略或利益相关者冲突 | `architecture-strategy-governance` | 目标和硬约束有来源，冲突和优先级明确 |
| 需要新的工作原理或候选概念 | `architecture-concept-development` | 真正不同的概念及保留/淘汰依据可比较 |
| 分组、耦合或接口成本过高 | `complexity-decomposition` | 分解有下一层关系证据及新增复杂度说明 |
| 选项组合、指标和决策互相影响 | `architecture-decision-optimization` | 可行候选、权衡、敏感度和模型局限明确 |

每次只加载解决当前缺口所需的专项 Skill，复用已有结论。已有系统先分析映射，新系统先明确价值和目标；只有输入存在依赖时才串联方法。记录关键决策和证据后，按所选模式检查输出；不会改变当前结论的其他分析不展开。

## 输出

按任务规模选择必要产物，不机械输出全部章节：

- 系统问题陈述、边界、环境和关键假设；
- 受益者/利益相关者、需求优先级、目标和价值通路；
- 无关特定方案的功能、候选概念及筛选理由；
- 形式、功能、映射、分解、接口和预期涌现；
- 架构决策、选项、约束、衡量指标、权衡和敏感度；
- 风险、验证方式、演化影响和未决问题。

将事实、假设、推断和决策分开标记。权重和优先级必须来自用户或可追溯依据；缺少会改变方案方向的信息时，列出歧义并集中提问。

## 完成检查

- 系统边界、外围环境、伴生系统和使用情境是否明确？
- 价值是否通过跨边界功能与操作数变化说明？
- 功能是否与特定解决方案解耦？
- 创建或选择架构时，是否比较了真正不同的概念，或说明唯一可行的硬约束？
- 涉及分解时，是否检查了下一层关系和多个分解平面？
- 关键接口、涌现行为和失效传播是否明确？
- 高影响决策是否有依据、敏感度和复审条件？
- 实际复杂度是否被压向必备复杂度，而非只隐藏表面复杂度？
