# 企业应用 5 视图

用同一个问题检查五个视图：业务职责如何被组织、数据如何被拥有和流动、代码如何承载、系统如何运行、资源如何部署。逻辑架构先启动，数据、开发、运行和物理视图根据约束并行深化。

## 五个视图

| 视图 | 关注点 | 必须回答 |
| --- | --- | --- |
| 逻辑架构 | 领域、用例、职责、边界和外部交互 | 谁负责什么？关键业务行为如何组合？ |
| 数据架构 | 数据实体、所有权、生命周期、存储、交换和治理 | 哪些数据是事实？谁写入、谁读取、谁负责质量？ |
| 开发架构 | 包、层、模块、框架、中间件、代码依赖和团队边界 | 代码如何隔离变化并支持协作、测试和发布？ |
| 运行架构 | 并发、状态、事务、缓存、消息、容错、观测和质量属性 | 关键场景如何运行和失败？ |
| 物理架构 | 节点、网络、环境、部署单元、资源和拓扑 | 什么被部署在哪里？故障和容量边界是什么？ |

## 执行协议

1. 先列出 Actor、用例、系统边界、领域责任、关键数据和质量属性场景。
2. 为每个视图建立最小模型，只保留影响决策的元素。
3. 建立跨视图追溯：
   - 用例 -> 逻辑职责；
   - 逻辑职责 -> 数据责任；
   - 逻辑职责/数据 -> 开发模块；
   - 质量场景 -> 运行机制；
   - 运行机制 -> 物理资源。
4. 检查常见冲突：领域边界与数据所有权不一致、代码层依赖反向、运行状态无归属、物理拓扑无法承载质量目标。
5. 为高影响冲突提出验证或决策，不用补图掩盖未知。

## 判断原则

- 不要求每个视图都达到同样的细节；细节应由决策风险决定。
- 不把逻辑边界自动等同于部署单元或微服务。
- 逻辑架构不是功能清单，而是角色通过系统达成目标的行为模型。
- 不把数据库表、代码包或云资源名称当成领域责任。
- 视图之间无法解释的关系必须成为风险、假设或未决问题。

## 最小交付

- 五视图摘要；
- 跨视图追溯矩阵；
- 冲突、假设和架构风险；
- 关键质量属性的运行/物理承载；
- 推荐决策与最小验证行动。
