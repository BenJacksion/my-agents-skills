# 领域与应用建模

先理解业务行为和边界，再决定对象、模块、数据和代码结构。领域模型不是数据库表的别名，也不是把所有名词都变成类。

## 执行协议

1. 区分用户目标、用例、业务规则、外部系统和非功能约束。
2. 从用例识别领域概念、状态变化、业务不变量、角色、事件和边界。
3. 明确数据的事实性、所有权、生命周期、敏感性、读写责任和一致性要求。
4. 形成逻辑模块和应用层职责，说明领域逻辑、用例编排、基础设施和接口适配的边界。
5. 比较分层、模块化单体、服务化等候选；不要先指定框架或 ORM。
6. 区分“新增功能”和“结构重构”两类变更；先保护功能正确，再用小步重构治理坏味道。
7. 用代表性用例检查模型：主流程、异常、并发修改、重试、补偿和审计是否有归属。
8. 输出从用例到领域、数据和代码模块的追溯，以及仍需验证的模型假设。

## 判断原则

- 用户界面流程不等于领域边界；数据库表也不等于领域对象。
- 领域边界要能解释业务规则、状态和数据责任，不能只按组织架构或页面切分。
- 应用层负责用例编排，领域层负责业务规则，基础设施负责外部技术细节；实际分层可因场景调整，但依赖方向必须有理由。
- 核心域优先承载业务行为；通用域和支撑域可以采用更简单的模型，不把充血/贫血当成教条。
- 聚合根负责守护不变量；跨聚合协作应显式说明事件、补偿或最终一致性。
- 不同限界上下文中的同名概念不必强行统一，跨上下文可用防腐层保护模型边界。
- 读模型、写模型、缓存和搜索索引只有在场景需要时引入。
- 同一业务规则不应因多个入口而重复实现；若确实重复，要记录一致性风险。

## 最小交付

- 用例表和关键场景；
- 领域概念、边界、状态和不变量；
- 数据所有权、生命周期和一致性说明；
- 逻辑/开发模块与依赖方向；
- 候选结构、取舍、验证行动和未决问题。
