# 分布式应用架构

先描述约束，再选择机制。每个分布式机制都要同时记录收益、新增复杂度和失效方式。

## 执行协议

1. 建立负载、峰值、延迟、吞吐、数据规模、可用性、故障域和一致性要求，并区分性能瓶颈、团队瓶颈、发布瓶颈和数据瓶颈。
2. 识别状态、数据所有权、事务边界、重试语义、幂等要求和消息顺序。
3. 比较集中式、模块化单体、异步化、服务化和分布式部署等候选。
4. 对缓存、内存数据库、消息队列、分布式事务、分布式数据库和微服务分别说明适用约束。
5. 检查跨服务调用、网络分区、重复消息、部分失败、回滚、观测、测试和运维成本；必要时明确限流、熔断、降级、幂等和最终一致性。
6. 设计代表性端到端场景和故障注入验证；不只验证单个服务存活。
7. 输出推荐方案、替代方案、迁移顺序、运行指标和复审条件。

## 判断原则

- 扩展性不只靠增加节点；数据、状态、锁、队列和外部依赖可能成为瓶颈。
- 微服务边界必须能解释业务责任、数据所有权、独立演进或故障隔离收益。
- 异步化会改变一致性、可见性、重试和补偿语义，不能只按性能收益描述。
- 限流保护系统，熔断阻止故障扩散，降级保护核心链路，幂等处理重试；四者不能互相替代。
- 分布式事务、跨服务查询和共享数据库都应列出长期代价。
- 机制选择必须保留简单方案作为基线，除非证据证明它不满足约束。

## 最小交付

- 负载、故障和一致性模型；
- 候选机制与收益/代价；
- 服务、数据、事务和消息边界；
- 关键故障场景、观测指标和验证方案；
- 迁移步骤、运行责任和复审条件。
