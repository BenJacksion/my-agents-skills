# 企业级应用架构

把企业应用架构视为一组相互追溯的总体决策，而不是一张架构图或一组技术名称：

```text
业务目标/用例
  -> 领域与逻辑
  -> 数据
  -> 开发
  -> 运行
  -> 物理
  -> 分布式、云和数据平台机制
```

## 工作模式

根据任务选择：

1. **新应用设计**：从目标、用例和领域边界开始建立 5 个视图。
2. **已有系统分析**：从当前代码、数据、运行和部署事实开始，识别视图断裂。
3. **架构决策**：比较集中式/分布式、单体/服务化、同步/异步、平台化/局部能力等候选。
4. **架构演进**：维护当前、目标和过渡结构，把非功能风险和改造顺序写成可验证行动。

## 执行协议

1. 开头区分事实、假设、未知、约束、决策人和成功标准。
2. 识别关键业务目标、用例、领域概念、数据责任和外部交互；不要从技术名词倒推架构。
3. 以逻辑架构为起点，建立或检查逻辑、数据、开发、运行和物理 5 个视图；其余视图可以并行深化，登记视图之间的冲突。
4. 把性能、可用性、一致性、安全、可观测性、扩展性和运维目标改写为质量属性场景。
5. 只有当负载、故障、交付、组织或数据约束支持时，才比较分布式、微服务、云和数据平台机制；保留简单基线作为对照。
6. 对关键用例、数据链路、故障场景和部署约束提出最小验证行动。
7. 输出推荐、替代方案、复杂度代价、演进步骤、复审条件和未决问题。

## 判断原则

- 5 个视图是同一个架构的不同投射，不是 5 份互不相干的图。
- 逻辑职责和数据责任先于服务数量、框架和部署节点。
- “高性能”“高可用”“可扩展”必须包含场景、响应和度量方式。
- 架构粒度应匹配业务复杂度、团队规模、组织边界和交付节奏。
- 微服务、云、消息和数据中台都是候选机制；没有证据时保留集中式或渐进式候选。
- 遗留改造先描述当前结构和过渡结构，不默认推倒重写。
- 架构图、文档完整度和单元测试都不能单独证明系统级正确性。

## 路由

- 5 个视图和跨视图一致性：`application-five-views`
- 用例、领域、DDD、分层、数据责任：`domain-application-modeling`
- 非功能、目标架构、遗留重构、架构演进：`evolutionary-architecture-modernization`
- 高并发、缓存、事务、消息、微服务：`distributed-application-architecture`
- 云、DevOps、Docker、Kubernetes、自动化运维：`cloud-native-delivery`
- 数据中台、采集、治理、ETL、数仓、标签、索引：`data-platform-architecture`

## 最小交付

- 当前问题、范围、事实、假设和约束；
- 用例、领域、数据和 5 视图的关键决策；
- 质量属性场景与承载方式；
- 技术机制的收益、代价和替代方案；
- 验证行动、演进步骤、复审条件和未决问题；
- 从业务目标到架构决策的追溯关系。
