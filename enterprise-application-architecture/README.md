# 《架构真意》企业级应用架构 Agents & Skills

本能力域根据范钢、孙玄《架构真意：企业级应用架构设计方法论与实践》的公开书目、目录和内容简介，提炼企业级应用从业务/领域到数据、代码、运行、部署、分布式和数据平台的架构能力。

原始研究见 [research.md](research.md)。研究文件区分来源明确的内容和本仓库的工程化综合提炼。

## 书籍定位

- 书名：《架构真意：企业级应用架构设计方法论与实践》
- 作者：范钢、孙玄
- 出版社：机械工业出版社
- 主要主题：架构设计方法论、分布式架构设计与实践、大数据架构设计。

本能力域不等同于完整复述原书，也不把《架构之道：软件构建的设计方法》混入本能力域。

## 一句话总结

企业应用架构要把业务目标和用例转成领域与数据责任，再通过开发、运行和物理视图承载质量属性；当访问量、并发、数据规模或组织协作发生变化时，再选择分布式、微服务、云和数据平台等机制，并用跨视图验证和演进计划控制复杂度。

## 能力链路

```text
业务目标与用例
  -> 领域与逻辑架构
  -> 数据架构
  -> 开发架构
  -> 运行架构
  -> 物理架构
  -> 分布式/微服务/云/数据平台
  -> 场景验证与架构演进
```

这不是固定的线性流程。已有系统通常从 `application-five-views` 或 `evolutionary-architecture-modernization` 开始；数据平台问题可以直接进入 `data-platform-architecture`；只有当分布式收益和约束已经明确时，才进入 `distributed-application-architecture`。

## 内容

- `research.md`：互联网研究、书籍摘要、证据边界和来源清单。
- `chapter-notes.md`：用户补充的逐章阅读笔记和可复用判断原则。
- `skills/`：总入口、5 视图设计、领域应用建模、演进与重构、分布式应用、云端交付和数据平台 Skills。
- `agents/`：企业应用总架构师、应用设计架构师、分布式与数据架构师。
- `capability-catalog.md`：能力地图、路由规则、状态契约和质量门。
- `agent-contracts.md`：Agent 输入、输出、交接和回退规则。

## 核心原则

- 先明确业务目标、用例、领域边界和数据责任，再选择技术。
- 5 个视图必须相互解释，不能用一张部署图代替完整架构。
- 非功能需求要写成可观察场景，并落到运行决策、物理资源和验证行动。
- 分布式、微服务、云和数据中台都是候选机制，不是默认答案。
- 架构演进要区分当前架构、目标架构、过渡架构和改造意图。
- 数据平台首先是数据责任、质量和消费闭环，其次才是工具和平台名称。
- 技术、估算和案例判断必须区分事实、假设、证据和决策。

## 与其他能力域的边界

- `system-architecture-product-design/`：系统边界、受益者、复杂系统概念、形式/功能映射和系统级权衡。
- `architecture-way/`：易变性分解、可组合架构、设计验证以及项目网络、时间/成本/风险。
- `enterprise-application-architecture/`：企业应用内部的 5 视图、领域/数据/开发/运行/物理架构，以及分布式、云和数据平台落地。

当企业应用架构问题改变了系统边界、产品概念或跨组织价值关系时，先交回系统架构能力；当问题进入架构与项目网络、关键路径或执行选项时，再组合 `architecture-way`。

需要从产品发现开始，或按完整软件生命周期串联全部能力时，参阅根目录的[软件工程流程](../software-engineering-process/README.md)。

## 使用方式

1. 阅读本目录的 `capability-catalog.md`，根据问题选择总入口或细分 Skill。
2. 新系统先从业务目标、用例和领域开始；遗留系统先识别当前 5 视图和关键断裂。
3. 对每个重要决定记录事实、假设、证据、权衡、验证行动和复审条件。
4. 不为填满 5 个视图而制造无效细节；只输出会改变决策的架构内容。
5. 需要项目网络、时间/成本/风险或跨系统边界时，交接给已有架构能力域。
