# 从业务问题到模型与项目设计

本页演示按[共用输入](inputs.md)逐步传递证据与决策，不是已经执行的客户项目。表中列出可能需要的能力，实际执行先选一个主阶段，只补当前缺口；多个角色不要求启动多个进程。

## S1：明确结果与风险假设

使用 `product-discovery`、`product-outcomes-metrics` 和 `product-assumption-testing`。

E1 只说明教学任务，尚无证据证明 G1 是主要用户问题。先观察调度员查找工单和选择人员的过程，再判断延迟来自资料分散、授权、人员不足还是其他原因。候选指标为可派单到成功提交的等待时长，配合误派单和改派率；U1 的基线、阈值与样本仍未知。

H1 的最小实验：在相同模拟任务中比较现有手动方式与候选人员辅助展示，先约定完成时间、错误类型和继续/停止标准；没有真实参与者与结果时仅交付实验设计。交接给架构的内容是教学场景、责任约束、候选结果和未知项，不是“用户已验证需要自动派单”。

## S2–S3：边界与候选概念

使用 `system-thinking-emergence`、`architecture-concept-development`，需要定量权衡时使用 `architecture-decision-optimization`。

系统边界包括工单与指派管理；人员名录、设备主档和通知接收方是外部交互方。核心功能是识别待办、判断可派人员、形成有效指派并反馈。人员不足造成的等待不能靠软件边界重划解决。

| 候选 | 工作方式 | 需要先验证的风险 |
| --- | --- | --- |
| 人工增强 | 整合工单与人员信息，调度员自行选择 | 信息是否足够，是否仍需频繁跨系统查找 |
| 辅助决策 | 展示符合规则的候选人员，由调度员确认 | 在岗数据是否及时、推荐是否影响判断 |
| 自动指派 | 系统按规则直接指派 | 规则例外、错误影响、授权及撤销责任 |

教学[效用权重分析](quantitative.md)用于展示不同偏好如何改变排序，不能作为真实业务采纳证据。暂将“辅助决策”保留为试验候选，人工方式作为对照；预算和规则证据未明确前，不确定自动指派为最终方案。

## S4：五视图与语义专项

以 `domain-application-modeling`、`application-five-views` 为应用设计能力，身份和历史查询使用 `ontology-modeling`。

| 视图 | 最小设计与跨视图关系 |
| --- | --- |
| 逻辑 | 工单模块负责指派；人员与设备由外部权威系统维护，通知不决定指派是否成立 |
| 数据 | 指派保存稳定身份、角色、有效区间与来源；工单模块唯一写入，RDF 如采用则为查询投影 |
| 开发 | 隔离人员名录、持久化和通知适配；模块边界不直接推导为独立服务部署 |
| 运行 | 指派时核实状态、权限与人员资格；处理并发和重复请求；通知结果独立跟踪 |
| 物理 | 先以既有应用与数据环境为候选部署基础；容量、故障恢复与可用性尚需实测 |

历史查询使用 `Assignment` 而非覆盖当前负责人。源人员记录与人员实体分别保留，以映射说明对应关系；不直接用姓名或 `owl:sameAs` 合并。具体模型、SHACL 与查询引用[可运行本体案例](../../../domains/ontology-modeling/skills/ontology-modeling/references/executable-example.md)，此处不复制一套模型。

教学案例验证的是原始数据和语义。E4 的实际授权、在岗判断以及 E5 的外部失败机制仍需实现证据。目标读写权威是设计决策，不表示已有系统已经完成对应改造。

## S5：变化、契约与项目网络

需要时使用 `volatility-decomposition` 和 `composable-architecture`：人员名录接口、指派资格规则和通知渠道可能独立变化。以实际变更历史确认这些易变点，再决定是否需要额外边界。

最小指派契约：输入工单与人员标识；执行端核实权限、Open 状态与人员资格；成功后旧 Primary 区间结束、新区间开始；冲突或条件不满足时拒绝。通知成功、失败与结果未知分别可见。版本条件和请求去重只是实现要求，不能假设目标平台已支持。

`project-design` 从这些设计和验证活动推导 A 数据契约、B 指派接口、C 历史映射、D 集成验收。活动估算与 CPM、资源冲突和权重敏感度见[定量案例](quantitative.md)。8/11 天是固定输入下的教学结果，实际排期还需可用资源、日历、等待和风险。

## S6–S8：实施交接、验收与反馈

实现交接带上[最小交付记录](deliverables.md)，由实际工程人员完成接口、存储、权限和外部集成。本仓库案例没有实施业务应用或部署 Foundry。

验收追溯：

| 输入/目标 | 设计决策 | 验证与当前边界 |
| --- | --- | --- |
| G1、H1 | 保留人工与辅助方式作对照 | 真实用户效果未验证 |
| E2、E3、G2 | 关联实体、稳定身份与有效区间 | 本体案例可复现历史查询、区间边界和 SHACL |
| E4、U2 | 执行端状态、资格与授权条件 | 目标环境未运行，禁止据本地数据检查宣称通过 |
| E5 | 对象提交与外部反馈分别记录 | 通知失败、超时与重试的真实行为未运行 |
| U3 | 架构与验证活动形成项目网络 | 定量脚本可复算，真实工期未确认 |

若运行反馈只有“改派覆盖了历史”，回到 S4 的数据/时间/映射，并检查相关更新契约；不重做未被推翻的产品目标。若实际访谈推翻 H1，再回到 S1。发布判断依据发布范围内的实际证据，不依据本页章节是否齐全。
